# Hosting and offline caching for the PWA and Region files

Research for ticket [021](../wayfinder/tickets/021-compare-hosting-options.md). Budgets come from ticket [011](../wayfinder/tickets/011-decide-target-devices-and-budget.md): ≤ 15 MB to reach mode select, ≤ 60 MB per Region-mode, an installable PWA, Android Chrome first and iOS 17+ Safari second. The file layout comes from ticket [006](../wayfinder/tickets/006-choose-engine-and-world-generation.md): 1 km chunk GLBs (meshopt), 3 levels of detail, plus Route and lane-graph JSON. A full offline set across Regions is assumed to be about 120–250 MB.

All pages were checked on **2026-10-26**. The "updated" date is the one the page itself shows; "n/d" means the page shows none. Nothing was signed up for or deployed.

## How this was checked

- Read each host's own limits, pricing and caching docs, plus MDN, web.dev, Chrome for Developers (Workbox) and the WebKit blog.
- Made a few HEAD requests and small `Range: bytes=0-9` GETs against public pages each host serves, to see real headers and which edge location answered. The requests came from the user's own connection, which appears to be in or near Bangladesh: Cloudflare answered from `DAC` (Dhaka) and `CGP` (Chittagong), Fastly/GitHub from `CCU` (Kolkata), Netlify from `aws-bom` (Mumbai), and Vercel from `bom1` (Mumbai). These are single observations, not latency measurements.
- Fetched 100 bytes of `threejs.org/examples/models/gltf/Soldier.glb`, a GitHub Pages site, to see how a `.glb` is served.

## Bandwidth arithmetic (facts, not a forecast)

| Host | Monthly free transfer | New players/month at 75 MB | At 250 MB |
|---|---|---|---|
| Cloudflare Pages / R2 | Unlimited static / free egress | — | — |

| Netlify Free | ~15 GB (minus deploys) | ~200 | ~60 |

A service-worker cache means returning players cost only revalidation requests: none at all for files marked `immutable`, or a 304 each if left at `max-age=0, must-revalidate`.

## Service-worker caching with Workbox

- **Precache size gate:** `maximumFileSizeToCacheInBytes` defaults to **2,097,152 bytes (2 MiB)**. Larger files are left out of the precache manifest unless this is raised ([workbox-build](https://developer.chrome.com/docs/workbox/modules/workbox-build), updated 2018-01-31).
- **Region downloads on demand:** files can be cached at runtime with a `CacheFirst` strategy and an `ExpirationPlugin`. `maxEntries` and/or `maxAgeSeconds` are required; `purgeOnQuotaError` is optional, defaults to `false`, and is recommended for runtime caches ([Understanding storage quota](https://developer.chrome.com/docs/workbox/understanding-storage-quota), updated 2018-06-26). Files can also be added explicitly with `cache.add()` / `warmStrategyCache` (an "offline Region" download button).
- **Range from cache:** if a Range request reaches the service worker, `workbox-range-requests` (`RangeRequestsPlugin`) can answer a 206 from a cached full 200 response. Only a full 200 should be cached, and the file must be cached ahead of time, because runtime caching of partial 206 responses doesn't work ([Serving cached audio and video](https://developer.chrome.com/docs/workbox/serving-cached-audio-and-video), updated 2021-12-07).
- **Opaque responses:** if Region files come from a different origin (e.g. an R2 custom domain) without CORS, the responses are opaque. Chrome counts "roughly 7 MB" of quota per opaque response, however small it is (same Workbox page). With CORS headers on the bucket and a CORS-mode fetch, a response counts at its real size.
- **Eviction is all-or-nothing per origin:** the shell precache and every Region cache on that origin are deleted together ([MDN quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria), last modified 2026-01-05).

## Storage quota and eviction: Android Chrome

Source: [MDN Storage quotas and eviction criteria](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria) (last modified 2026-01-05); [web.dev Storage for the web](https://web.dev/articles/storage-for-the-web) (updated 2024-09-23); [web.dev Persistent storage](https://web.dev/articles/persistent-storage) (updated 2020-05-12).

- **Quota:** an origin can store up to **60% of total disk**, in both best-effort and persistent modes. Chrome as a whole uses at most 80%. The quota is based on total disk, not free space, so a write can still fail on a nearly full phone. On a 64 GB phone, 60% is about 38 GB, far above 250 MB.
- **Reduced quotas:** incognito gets about 5% (web.dev), or "about 100 MB" (Workbox page). If "Clear cookies and site data when you close all windows" is on, the quota is about 300 MB (web.dev).
- **Eviction:** best-effort origins are removed least-recently-used first, under storage pressure or when Chrome's 80% cap is exceeded. Persistent origins are evicted only when the user clears them.
- **`navigator.storage.persist()`:** there is no prompt. Chrome grants or denies it silently. Its heuristics "include" site engagement, **whether the site is installed or bookmarked**, and notification permission. A denied request can be retried later. An installed PWA is one of the listed signals, but the docs don't promise a grant.
- **`estimate()`:** Chrome reports 60% of disk as `quota`, which can be more than is actually free. `QuotaExceededError` must still be handled.

## Storage quota and eviction: iOS Safari (17+)

Source: [WebKit, Updates to Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/) (2023-08-10); [WebKit, Full Third-Party Cookie Blocking and More](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/) (2020-03-24); MDN (as above).

- **Quota (iOS 17 / Safari 17 and later):** an origin can use up to **60% of disk** in a browser app. **Home Screen web apps get the same quota as the browser.** All origins together are capped at 80%. Cross-origin frames get 10% of the parent's quota. Other WebKit apps (WKWebView) get 15% per origin. Safari 17 no longer prompts for more space. Writes over quota fail with `QuotaExceededError`. (Before 17, there was a 1 GiB initial quota and then a prompt; web.dev's "about 1 GB" figure describes that older behaviour.)
- **Eviction:** LRU per origin when the overall quota is exceeded, under system storage pressure, or after a period of non-use under ITP. Origins with an active page, or in persistent mode, are excluded.
- **7-day cap on script-writable storage (ITP):** when cross-site tracking prevention is on, Safari deletes all script-written data (including the Cache API and IndexedDB) for a site with no user interaction in the last 7 days of Safari use. **Home Screen web apps** "are not part of Safari and thus have their own counter of days of use", and WebKit does not expect their first-party data to be deleted (WebKit 2020). web.dev also says the cap "doesn't apply to installed PWAs". MDN doesn't say either way.
- **Separate container:** a Home Screen web app has its own storage, separate from Safari tabs (web.dev). Regions cached in a Safari tab are **not** visible to the installed app, and vice versa.
- **`persist()`:** no prompt. WebKit decides by heuristics, and its example is **whether the site is opened as a Home Screen Web App**. It "does not guarantee approval". Persistent origins are excluded from eviction.
- **EU (iOS 17.4+):** browsers with other engines follow their own rules. Not relevant to Safari itself.

## Implications (facts and trade-offs for ticket 022)

- **Bandwidth ceiling:** Cloudflare (Pages static assets, and R2 egress) is the only option with no transfer cap. GitHub Pages and Vercel give about 100 GB/month. Netlify (~15 GB) and Firebase (10 GB) are the tightest, and both **take the whole site offline** when exceeded.
- **Proximity to Bangladesh:** only Cloudflare has PoPs in Bangladesh (Dhaka and Chittagong, both observed). GitHub Pages (Fastly) was served from Kolkata. Netlify and Vercel were served from Mumbai.
- **File size:** 1 km chunk GLBs are expected to be well under every cap. The tightest are Cloudflare's 25 MiB hard cap and Netlify's 10 MB "not well-supported" threshold. A single larger file, such as a texture atlas or a merged landmark pack, would need checking against these.
- **Total size:** a 120–250 MB asset set fits GitHub Pages (1 GB), Cloudflare (20,000 files) and Firebase (10 GB). It **exceeds Vercel Hobby's 100 MB per CLI deploy**. The docs state no equivalent limit for Git-built deploys. Vercel Hobby also bars commercial use, such as ads.
- **Cache headers:** with Cloudflare, Netlify and Vercel, fingerprinted chunk names can be served as `immutable` with a one-year max-age. GitHub Pages is fixed at `max-age=600`, so after 10 minutes every request revalidates. With a service worker and `CacheFirst`, this matters less after the first download.
- **Range requests:** Cloudflare Pages/Workers answer ranges with a full 200. GitHub, Netlify and Vercel return 206. This only matters if the game reads part of a file; whole-file chunk GLBs don't.
- **Split hosting (Pages for the shell, R2 for Regions):** the R2 bucket needs a custom domain on Cloudflare. `r2.dev` is rate-limited and uncached. It also needs a cache rule for `.glb` (not cached by default) and CORS headers, so service-worker caches don't fill with opaque responses at ~7 MB each in Chrome.
- **Workbox:** the ≤ 15 MB shell can be precached, but any file over 2 MiB is skipped unless the limit is raised. Region chunks fit runtime or explicit caching with `ExpirationPlugin`. Eviction removes the whole origin at once, shell included.
- **Quota is not the constraint on either browser:** 60% of disk on both Android Chrome and iOS 17+ Safari, installed or not. The risks are **eviction** (best-effort data on a full phone; Safari's 7-day ITP rule for non-installed use) and **iOS's separate container** (a Region cached in a Safari tab must be downloaded again after "Add to Home Screen").
- **`persist()`:** on both browsers it is silent and heuristic. Installation is a listed positive signal on Chrome and the named example on WebKit, but neither promises a grant. The game can only call it, check `persisted()`, and handle a denial.
